Sécurité

Un serveur RMM peut contrôler chaque ordinateur qu'il gère. RMMZit est conçu pour qu'un attaquant qui atteint la console, le réseau ou même le serveur obtienne le moins possible.

Comment RMMZit vous protège

  • Deux ports. La console et le point d'accès des agents écoutent sur des ports séparés. La console n'accepte que les connexions des réseaux autorisés, vérifiées avant TLS ; le port des agents peut être public sans exposer la console.
  • Agents sortants. Les agents se connectent au serveur ; les ordinateurs gérés n'ont besoin d'aucun port ouvert. Les agents épinglent le certificat du serveur par son empreinte, un faux serveur ne peut donc pas en prendre le contrôle.
  • Commandes signées. Chaque commande vers un agent est signée avec la clé de commande du serveur et vérifiée par l'agent ; les mises à jour des agents doivent correspondre au SHA-256 d'une commande signée.
  • Connexion forte. Connexion à deux facteurs pour chaque compte local et d'annuaire, mots de passe argon2id, sessions courtes, déconnexion après inactivité, blocage progressif des connexions échouées.
  • Protections du navigateur. Vérifications CSRF à chaque modification, Content Security Policy stricte sans scripts en ligne, cookies de session __Host-.
  • Moindre privilège. Rôles et accès par client ; la console tourne sous un utilisateur non privilégié, et les rares actions root (mises à jour, réseau, fuseau horaire) passent par un assistant root séparé qui n'accepte que des demandes fixes et validées.
  • Audit. Un journal d'audit chaîné par hachage de chaque modification et de chaque action à distance.
  • Versions signées. Le serveur, les agents et install.sh n'installent que des versions signées avec la clé de publication RMMZit.
  • Secrets. Les mots de passe enregistrés (e-mail, LDAP, canaux, Cloudflare) sont chiffrés avec la clé secrète du serveur ; le diagnostic retire les secrets.

Bonnes pratiques

  1. Ne rendez la console accessible que depuis vos réseaux d'administration ; pour un accès extérieur, utilisez un VPN (par exemple WireGuard) plutôt que d'ouvrir le port de la console.
  2. N'ouvrez le port des agents que là où se trouvent les agents, et définissez les réseaux des agents si tous viennent d'adresses connues.
  3. Utilisez un certificat reconnu par les navigateurs (Let's Encrypt ou votre AC) pour que les utilisateurs ne prennent pas l'habitude d'ignorer les avertissements.
  4. Donnez à chacun son propre compte avec le rôle le plus restreint et seulement les clients nécessaires ; désactivez les comptes des personnes qui partent.
  5. Gardez un administrateur local pour les urgences, avec ses codes de récupération conservés hors ligne.
  6. Installez rapidement les mises à jour de RMMZit (ou activez les mises à jour automatiques) et maintenez à jour le système du serveur ; l'appliance installe elle-même les mises à jour de sécurité de Debian.
  7. Sauvegardez régulièrement la base de données et /var/lib/rmmzit, et gardez la sauvegarde loin du serveur.
  8. Consultez le journal d'audit de temps en temps, et laissez activé l'avis sur l'écran distant pour que les utilisateurs sachent quand quelqu'un est connecté.

Merci de signaler les problèmes de sécurité de manière confidentielle via GitHub → Security → Report a vulnerability, et non dans un ticket public.
