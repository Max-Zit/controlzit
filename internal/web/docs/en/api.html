API

The REST API lets scripts and other tools read devices, alerts and tasks and start work on devices, with the same rights as in the console.

Tokens

Create a token under My account → API tokens: a name, a role no higher than yours (read-only, technician or administrator) and how long it is valid. The token is shown once; store it like a password. It acts as you, with your customers. Send it in every request as Authorization: Bearer czt_… to the console address (port 8443), which accepts connections only from the allowed networks. Session cookies of the browser do not work on the API. Deleting the token on the account page ends its access at once.

Calls

CallWhat it does
GET /api/v1/mewho the token acts as, its role and customers
GET /api/v1/customerscustomers
GET /api/v1/customers/{id}/sitessites of a customer
GET /api/v1/devices?customer=&site=&q=devices, optionally filtered by customer, site or a search text
GET /api/v1/devices/{id}one device with its inventory
GET /api/v1/devices/{id}/tasksthe tasks of a device (running, waiting and the newest 100 finished)
POST /api/v1/devices/{id}/tasksstart a task on a device (technician)
GET /api/v1/tasks/{id}one task, to follow it until it ends
POST /api/v1/tasks/{id}/cancelstop a running or cancel a waiting task (technician)
GET /api/v1/alerts?state=openopen alerts (state=all also resolved ones)
GET /api/v1/softwarepackages of the software library (technician)
POST /api/v1/software/{id}/installinstall a library package on devices, as a job (technician)
GET /api/v1/jobs/{id}the result of a job per device (technician)
GET /api/v1/policiespolicies with their assignments (administrator)
POST /api/v1/policies/{id}/assignassign a policy to customer:ID, site:ID or device:ID (administrator)
POST /api/v1/policies/unassignremove the policy of a customer, site or device (administrator)

Tasks

A task waits until the device is online and runs after the device's earlier tasks, just like the actions in the console; it shows under the device's Activity. The answer is 202 with the task; follow it with GET /api/v1/tasks/{id} until its status is done, failed, cancelled or expired. The kinds and their fields:

{"kind": "script", "shell": "powershell", "script": "Get-Service Spooler", "timeout": 120}
{"kind": "patch.scan"}
{"kind": "patch.install", "updates": [], "reboot": false}
{"kind": "winget", "action": "install", "id": "7zip.7zip"}
{"kind": "choco", "action": "upgrade", "id": "firefox"}
{"kind": "power", "action": "restart", "delay": 300, "message": "Restart for updates"}
{"kind": "agent.update"}
{"kind": "bitlocker.keys"}

Examples

A PowerShell script on device 9, then its result:

curl -s -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"kind":"script","shell":"powershell","script":"Get-Date","timeout":60}' \
  https://rmm.example.com:8443/api/v1/devices/9/tasks
curl -s -H "Authorization: Bearer $TOKEN" https://rmm.example.com:8443/api/v1/tasks/42

$h = @{ Authorization = "Bearer $env:CZ_TOKEN" }
Invoke-RestMethod -Headers $h https://rmm.example.com:8443/api/v1/alerts

Errors

Errors come as JSON {"error": "…"} with the HTTP status: 400 for a bad request, 401 for a missing, wrong or expired token, 403 when the token's role does not allow the call, 404 for something that does not exist or that the token may not see, 409 when a task has already ended, 429 after too many failed sign-ins from the address. Every change through the API is recorded in the audit log with the token's name.
