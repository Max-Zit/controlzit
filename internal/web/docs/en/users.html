Users, roles and sign-in

Every person signs in with their own account. Roles decide what they may do, customer access decides what they may see, and every action is written to the audit log with their name.

Roles

RoleMay
Administratoreverything, including users and settings; always sees all customers
Technicianmanages the devices of the allowed customers: remote access, scripts, updates, programs, alerts
Read-onlyonly views the allowed customers: devices, alerts, updates, reports

Technicians and read-only users get access to all customers (also future ones) or only some customers.

Local accounts

Under Users an administrator adds a user with an initial password; the user must change it and set up two-factor sign-in at the first sign-in. An administrator can disable a user (open sessions end), set a new password, or reset two-factor sign-in for a user who lost the phone and the recovery codes. At least one enabled administrator always remains.

Two-factor sign-in

RMMZit has administrator access to every managed computer, so every local and directory account needs an authenticator app (Microsoft Authenticator, Google Authenticator, Authy, 1Password, Bitwarden …). Each account also gets 10 single-use recovery codes; new ones can be made under Account. Failed sign-ins block the address for a while (longer after each repeated block); the limits are under Settings → Sign-in and security, together with the session length and the sign-out after inactivity.

Active Directory / LDAP

Under Settings → Active Directory / LDAP users sign in with their directory account. The directory checks the password; RMMZit still asks for its own second factor.

  • Server: ldaps://dc1.example.local (port 636), or ldap:// (389) with StartTLS — passwords never cross the network unencrypted. Add the CA certificate if the directory's certificate comes from a company CA.
  • Service account (DN or user@domain) and its password, the base DN and the user filter, e.g. (&(objectClass=user)(sAMAccountName={username})) for Active Directory.
  • Groups and roles: map directory groups to Administrator, Technician and Read-only; the highest role wins. Nested groups of Active Directory can be included.
  • Customer groups: lines group = customer limit technicians and read-only users to those customers.

Test checks a directory account with the saved settings, without signing in, and shows what RMMZit would make of it. Directory accounts change their password in the directory, not in RMMZit.

Single sign-on (OpenID Connect, SAML)

Under Settings → Single sign-on users sign in with their account at an identity provider: OpenID Connect (Microsoft Entra ID, Google, Okta, Keycloak …) or SAML 2.0 (ADFS, Entra ID, Okta …). The sign-in page then shows a button.

  • OpenID Connect: register an application at the provider with the redirect URI shown on the page, then enter the issuer (e.g. https://login.microsoftonline.com/<tenant>/v2.0), the client ID and the client secret.
  • SAML: give the provider the console's metadata (link on the page) or its entity ID and reply (ACS) address, then enter the provider's metadata URL or paste its metadata XML.
  • The groups claim carries the groups (names or IDs; Entra ID sends group IDs), mapped to roles and customers as with LDAP.
  • The identity provider's own multi-factor policy applies; optionally RMMZit asks for its own second factor too.

Local accounts keep working when LDAP or single sign-on is on, so an administrator can always sign in. Keep one local administrator for emergencies.

Audit log

Audit log lists every change and every remote action with the user, the target (customer, site, device or user, with a link) and the address. The entries are hash-chained; the console checks the chain on every view and reports if an entry was changed or deleted.
