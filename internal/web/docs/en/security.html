Security

An RMM server can control every computer it manages. RMMZit is built so that an attacker who reaches the console, the network or even the server gets as little as possible.

How RMMZit protects you

  • Two ports. The console and the agent endpoint listen on separate ports. The console accepts connections only from allowed networks, checked before TLS; the agent port can be public without exposing the console.
  • Outbound agents. Agents connect to the server; managed computers need no open ports. Agents pin the server certificate by its fingerprint, so a fake server cannot take them over.
  • Signed commands. Every command to an agent is signed by the server's command key and checked by the agent; agent updates must match the SHA-256 in a signed command.
  • Strong sign-in. Two-factor sign-in for every local and directory account, argon2id passwords, short sessions, sign-out after inactivity, progressive blocking of failed sign-ins.
  • Browser protections. CSRF checks on every change, a strict Content Security Policy without inline scripts, __Host- session cookies.
  • Least privilege. Roles and per-customer access; the console runs as an unprivileged user, and the few root actions (updates, network, time zone) go through a separate root helper that accepts only fixed, validated requests.
  • Audit. A hash-chained audit log of every change and every remote action.
  • Signed releases. The server, the agents and install.sh install only releases signed with the RMMZit release key.
  • Secrets. Stored passwords (email, LDAP, channels, Cloudflare) are encrypted with the server's secret key; diagnostics remove secrets.

Best practices

  1. Keep the console reachable only from your admin networks; use a VPN (for example WireGuard) for access from outside instead of opening the console port.
  2. Open the agent port only where agents are, and set the agent networks if all agents come from known addresses.
  3. Use a certificate browsers trust (Let's Encrypt or your CA) so that users learn not to click through warnings.
  4. Give each person their own account with the smallest role and only the customers they need; disable accounts of people who leave.
  5. Keep one local administrator for emergencies, with its recovery codes stored offline.
  6. Install RMMZit updates soon (or switch on automatic updates) and keep the server's operating system updated; the appliance installs Debian security updates by itself.
  7. Back up the database and /var/lib/rmmzit regularly, and keep the backup away from the server.
  8. Check the audit log from time to time, and leave the notice on the remote screen on so users know when someone is connected.

Reporting a vulnerability

Please report security problems privately through GitHub → Security → Report a vulnerability, not in a public issue.
